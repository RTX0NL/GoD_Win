## Config file anatomy

A config file is a JSON object with these top-level keys:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `name` | string | yes | Human-readable label for the config. |
| `description` | string | no | Free-text description. |
| `settingsFile` | path string | no | Path to a separate [settings file](#settings-file). |
| `rootFolder` | path string | yes | Working directory that all operation paths resolve against. |
| `operations` | array | yes | Ordered list of operations (see below). |

`rootFolder` is resolved **relative to the config file's own location** — the
generated configs use `".."`, meaning "the project folder above `/Config`".
Every path inside an operation (e.g. `"./Build/Contents"`) then resolves from
that root.

Each entry in `operations` is a wrapper with an enable toggle:

```json
{
  "enabled": "YES",
  "operation": { "<operationName>": { … } }
}
```

- Operations run **in array order**; only entries with `enabled: "YES"` run.
  Disabled entries stay in the file as ready-to-enable templates.
- `enabled` is a string: `"YES"`/`"Yes"`/`"yes"`/`"TRUE"`/`"True"`/`"true"`
  enable; anything else (including `"NO"`) disables.

Operations come in two structural shapes:

- **Container operations** hold their own nested `operations` array, with
  per-item toggles of the same shape (`gamecubeDump`, `gamecubeBuild`,
  `wiiDump`, `wiiBuild`, `coloXDDump`, `coloXDBuild`, `pbrDump`, `gciDump`,
  `gciBuild`, `xdSaveDump`, `xdSaveBuild`, `coloSaveDump`, `coloSaveBuild`,
  `pbrBuild`, `convert`):

  ```json
  { "coloXDDump": { "config": { "operations": [
      { "enabled": "YES", "operation": { "dumpXD": { … } } }
  ] } } }
  ```

- **Flat operations** hold a plain field object (`dolDisassembly`,
  `dolAssembly`, `relDisassembly`, `relAssembly`, `commonRelDump`,
  `commonRelBuild`, `relsDump`, `relsBuild`, `cisoDump`, `cisoBuild`, `nkitDump`, `nkitBuild`,
  `rvzDump`,
  `nintendoArchiveDump`, `nintendoArchivesDump`, `nintendoArchiveBuild`,
  `nintendoArchivesBuild`, `pbrFontDump`, `pbrFontsDump`, `pbrFontBuild`,
  `pbrFontsBuild`, `pbrStringsDump`, `pbrStringsBuild`, `compress`,
  `decompress`, `compressFiles`, `decompressFiles`):

  ```json
  { "dolDisassembly": { "config": {
      "dolPath": "./Build/Contents/sys/main.dol",
      "outputFolder": "./Source/Code",
      "dolphinEngine": "./Engines/Dolphin Engine"
  } } }
  ```

## Settings file

The file referenced by `settingsFile` (conventionally
`/Settings/Settings.json`):

| Key | Type | Default | Meaning |
|---|---|---|---|
| `verbose` | bool | `false` | Emit detailed logging. |
| `wiiCommonKeyFile` | path string | — | Path to a text file containing the Wii common key (hex). Required for Wii ISO decrypt/encrypt. The key is **never** stored in this repository; supply your own. |

Both keys may be omitted. If the settings file is missing or invalid, defaults
are used.

## JSON conventions

- **Paths are plain strings.** Fields documented as *path* accept relative
  (resolved against `rootFolder`) or absolute paths.
- **Keys are verbatim Swift names.** No case conversion is applied.
- **Enum payloads** encode as a single-key object named after the case. Cases
  without fields use an empty object (`{ "all": {} }`); unlabeled values use
  `_0` keys (`{ "onlyPrefixes": { "_0": ["B1_"] } }`).
- **Optional fields** may be omitted or set to `null`. Fields listed as
  required below must be present — including booleans like `overwrite` whose
  Swift initializers have defaults (initializer defaults do not apply when
  decoding JSON).
- **Engine fields** (`dolphinEngine`, `gamecubeEngine`, `wiiEngine`,
  `geniusSonorityEngine`, `gameEngine`, `xdEngine`, `colosseumEngine`) are
  folder paths pointing at an engine definition folder, e.g.
  `"./Engines/Dolphin Engine"`. Project setup exports these automatically.

**`coloXDDump`** *(container)* — extract Genius Sonority assets from an
unpacked disc. Nested operations:

- `dumpColosseum` / `dumpXD` — full asset extraction pass over the Contents
  folder (FSYS archives → organized asset folders + FST registry).
  | Field | Type | Meaning |
  |---|---|---|
  | `fstFolder` | path | Unpacked Contents folder. |
  | `outputFolder` | path | Output folder for extracted assets. |
  | `overwrite` | bool | Replace existing output. |
  | `dolphinEngine` | path | Dolphin engine folder. |
  | `geniusSonorityEngine` | path | Genius Sonority engine folder. |
- `unpackFSYS` — extract a single FSYS archive.
  | Field | Type | Meaning |
  |---|---|---|
  | `fsysFile` | path | Input `.fsys`. |
  | `outputFolder` | path | Output folder. |
  | `overwrite` | bool | Replace existing output. |
  | `geniusSonorityEngine` | path | Genius Sonority engine folder. |
- `dumpFonts` / `dumpFlashMenus` / `dumpMessages` / `dumpATXs` / `dumpAudios`
  — batch-convert a folder of one asset kind to editable artifacts
  (JSON + PNG/PGM/WAV):
  | Field | Type | Meaning |
  |---|---|---|
  | `fontsFolder` / `flashMenusFolder` / `messagesFolder` / `atxFolder` / `audioFolder` | path | Input folder of `.fnt` / `.gsw` / `.msg` / `.atx` / `.ish`+`.isd` files. |
  | `outputFolder` | path | Output folder. |
  | `overwrite` | bool | Replace existing output. |
  | `variant` | string | (`dumpMessages` only) `"xd"` or `"colo"` — control-code dialect. |
- `dumpFlashMenu` / `dumpMessage` / `dumpATX` / `dumpAudio` — single-file
  variants of the above (`gswFile` / `msgFile` + `variant` / `atxFile` /
  `ishFile` + `isdFile` respectively, plus `outputFolder`, `overwrite`).
- `dumpColoScripts` — decompile every `.scd` under a folder to source text.
  Colosseum only; XD's script dialect has no compiler yet.
  | Field | Type | Meaning |
  |---|---|---|
  | `scriptsFolder` | path | Input folder of `.scd` files. Searched recursively, so Colosseum's `Battlefields/` subfolder is mirrored into the output. |
  | `outputFolder` | path | Output folder for the source files. |
  | `overwrite` | bool | Replace existing output. |
  | `language` | string | `"python"` or `"swift"` — which dialect to emit. Either one recompiles to the same bytecode. |
  | `gameEngine` | path | Colosseum engine folder. Supplies the builtin function signatures the source names. |
  | `engines` | [path]? | Engine folders whose enums resolve a signature's `enumRef` parameter types, consulted in order (first match wins). Absent = just `gameEngine`, which carries every enum its own signatures currently name. |
- `dumpColoScript` — single-file variant (`scdFile` in place of
  `scriptsFolder`, same remaining fields).

**`coloXDBuild`** *(container)* — rebuild Genius Sonority assets and repack.
Nested operations:

- `buildColosseum` / `buildXD` — full rebuild pass: repack FSYS archives from
  the asset folders and write them into the Contents folder.
  | Field | Type | Meaning |
  |---|---|---|
  | `fstRegistry` | path | The `FST.json` registry written by the dump pass. |
  | `outputFolder` | path | Contents folder to write into. |
  | `overwrite` | bool | Replace existing files. |
  | `dolphinEngine` | path | Dolphin engine folder. |
  | `geniusSonorityEngine` | path | Genius Sonority engine folder. |
- `packFSYS` — repack a single FSYS archive.
  | Field | Type | Meaning |
  |---|---|---|
  | `registryFile` | path | The archive's registry JSON. |
  | `sourceFolder` | path | Folder holding the archive's member files. |
  | `outputFile` | path | Output `.fsys`. |
  | `overwrite` | bool | Replace existing output. |
  | `geniusSonorityEngine` | path | Genius Sonority engine folder. |
- `buildGSfsysTOC` — regenerate the `GSfsys.toc` table of contents
  (`fstRegistry`, `outputFile`, `overwrite`, `geniusSonorityEngine`).
- `buildFST` — regenerate `fst.bin` from a Contents folder
  (`contentsFolder`, `outputFile`, `overwrite`, `dolphinEngine`).
- `buildFonts` / `buildFlashMenus` / `buildMessages` / `buildATXs` /
  `buildAudios` — batch-rebuild one asset kind from its editable artifacts
  (`fontsFolder` / `projectsFolder` / `jsonFolder`, plus `outputFolder`,
  `overwrite`).
- `buildFont` / `buildFlashMenu` / `buildMessage` / `buildATX` / `buildAudio`
  — single-file variants (`metadataFile` / `jsonFile` in; `outputFile` — or
  `ishOutputFile` + `isdOutputFile` for audio — out; plus `overwrite`).
- `buildColoScripts` — compile a folder of script source back to `.scd`.
  Reads `.py` and `.swift` alike, since both dialects describe the same
  bytecode. Write the output back over the unpacked `.scd` files and run it
  *before* the FSYS pack, which is the only thing that writes archives.
  | Field | Type | Meaning |
  |---|---|---|
  | `sourceFolder` | path | Input folder of script source. |
  | `outputFolder` | path | Where the rebuilt `.scd` files go. |
  | `overwrite` | bool | Replace existing files. |
  | `gameEngine` | path | Colosseum engine folder. |
  | `engines` | [path]? | Engine folders resolving `EnumName.case` constants in the source, in order. A constant naming an enum none of them declares fails the build rather than compiling to a guess. |
- `buildColoScript` — single-file variant (`sourceFile`, `outputFile`,
  `overwrite`, `gameEngine`, `engines`).

**`pbrStringsDump`** *(flat)* — dump every PBR string into one editable document.

PBR addresses a string by a global id, stores it in one of four `MESG`
tables, and ships each table once per language — so the one question an
editor has ("what does string 11 say?") is the one the disc's own layout
hides. The document inverts that: a section per table, a row per id, and
that id's text in every language on the row. Everything derivable is
derived — a table's id is its position, a string's index is its row's
position, and the directory that maps id → (table, index) is rebuilt on
build rather than edited. Ids are therefore the only stable reference, and
a row can move without changing what an id means.

Nothing is shared with the Colosseum/XD message operations: the two formats
have an extension in common and nothing else.

| Field | Type | Meaning |
|---|---|---|
| `unpackedFolder` | path | The unpacked project folder; file references in the document are relative to it. |
| `messagesFolder` | path | Folder of `.msg` binaries the unpack wrote, language subfolders included. |
| `directoryFile` | path | The `common.fsys` member holding the string directory (`common_091.bin` on US/PAL, `common_119.bin` on JP). |
| `outputFile` | path | The document to write. |
| `overwrite` | bool | Replace existing output. |

**`pbrStringsBuild`** *(flat)* — rebuild the `.msg` binaries and the string directory from the document.

Writes only the loose binaries in the unpacked tree, so it belongs ahead of
`pbrBuild`, which is what packs them into the archives. Each target is read
before it is written — it carries a header field the document doesn't, and
it says which table and language it holds, so writing over the wrong file
fails instead of shipping.

Editing rules the build enforces, each failure naming the id that caused it:
ids run from 1 with no gaps (the directory is an array indexed by id, so new
strings go at the end and a string is retired by blanking its text, not by
removing it); an id belongs to exactly one table; and a language's text is an
unbroken run from the start of its table — a language may stop before the
table ends, as English outruns the others on a US disc, but it cannot skip a
string and resume, because that would shift every later index for it. A
table the directory declares but the disc doesn't ship (JP's fourth) keeps
its slot as a section with no files and no strings, so the tables after it
aren't renumbered.

| Field | Type | Meaning |
|---|---|---|
| `stringsFile` | path | The document `pbrStringsDump` wrote. |
| `unpackedFolder` | path | The unpacked project folder its file references resolve against. |
| `overwrite` | bool | Replace existing files. |

### DOL executable

**`dolDisassembly`** *(flat)* — disassemble `main.dol` into per-section

|---|---|---|
| `dolPath` | path | Input `.dol`. |

**`dolAssembly`** *(flat)* — reassemble `main.dol` from a source folder.

An edit that changes a chunk's size moves every symbol after it within that
section. The symbol map is where the next disassembly reads addresses from,
and the type map names its tables by label, so a map left at the pre-build
addresses would have the next dump type the wrong bytes. That is what
`outputSymbolMapPath` is for: it re-emits the map with the addresses this
assembly produced, and project setup points it at the input map so the two
stay in step. Point it somewhere else to keep the original, or leave it out
to write no map at all.

| Field | Type | Meaning |
|---|---|---|
| `codeFolder` | path | Input source folder (from `dolDisassembly`). |
| `outputDolPath` | path | Output `.dol`. |
| `symbolMapPath` | path *(optional)* | Symbol map. |
| `outputSymbolMapPath` | path *(optional)* | Where to write the map the assembly produced. Usually `symbolMapPath` itself. |
| `typeMapPath` | path *(optional)* | Type map for typed data-section import. |
| `engines` | paths *(optional)* | Engine folders whose structs resolve the type map's chunk types. |
| `bssEntryListPath` | path *(optional)* | BSS entry list file. |
| `dolphinEngine` | path | Dolphin engine folder. |

### Routed RELs

Every REL a project unpacks other than `common.rel` — the maps, the menu
modules, `tableres2.rel` — is described by the game engine's **REL route
table**, `Resources/rel_routes.json`. It has three parts: named `matchers`,
each an optional type map and an optional pointer-index symbol index (paths
relative to the engine folder); `routes`, which map each REL's full path in
the unpacked tree to the matcher describing it; and `ignored`, RELs another
operation owns. A game ships a few hundred RELs and a handful of layouts, so
many routes share one matcher:

```json
{
  "matchers": {
    "map_char_pos_resource": {
      "symbolIndex": "Resources/map_symbols_char_pos_resource.json" },
    "prototypeMap_resource": {
      "symbolIndex": "Resources/map_symbols_resource.json" },
    "untyped": {}
  },
  "routes": {
    "/Data/Relocatable Modules/D1_labo_1F.rel":      "map_char_pos_resource",
    "/Assets/Misc/TEST000/TEST000.rel":              "prototypeMap_resource",
    "/Data/Relocatable Modules/French/pda_menu.rel": "untyped"
  },
  "ignored": ["/Assets/Data/Common/common.rel"]
}
```

A matcher with neither file still disassembles its RELs, untyped and with
positional `sym_N` names. Keys are full paths because a stem isn't unique
(`pda_menu.rel` sits in every language folder) and because the unpack doesn't
put every REL in one folder (a map archive's REL lands in that archive's own
folder). Adding a REL, or moving one to another layout, is an edit to this
file.

**`relsDump`** *(flat)* — disassemble every REL the route table names into a
source tree that mirrors the unpacked one.

| Field | Type | Meaning |
|---|---|---|
| `routesPath` | path | The route table. |
| `routesEngine` | path | Engine folder the matchers' paths resolve against. |
| `inputFolder` | path | Root the route keys are relative to (the unpacked tree). |
| `outputFolder` | path | Source root: each REL lands at its route path minus `.rel`, e.g. `<outputFolder>/Data/Relocatable Modules/D2_out/`. |
| `overwrite` | bool | Replace a REL's source if it already has a manifest; `false` leaves it alone. |
| `dolphinEngine` | path | Dolphin engine folder. |
| `dolSymbolMapPath` | path *(optional)* | DOL symbol map for cross-module relocation targets. |
| `engines` | paths *(optional)* | Engine folders whose structs resolve the type maps' chunk types. Absent = `routesEngine`. |

A route naming a file the project doesn't have is skipped with a warning,
since regions differ (JP ships no `tableres2.rel`) but a wrong path looks the
same. A `.rel` anywhere in the unpacked tree that neither a route nor
`ignored` names is warned about too. A matcher naming a type
map or symbol index that doesn't exist fails the RELs routed to it rather
than dumping them untyped. Every REL is attempted and failures are reported
together at the end.

**`relsBuild`** *(flat)* — reassemble every routed REL whose source folder
exists back to the path its route names.

| Field | Type | Meaning |
|---|---|---|
| `routesPath` | path | The route table. |
| `inputFolder` | path | Source root `relsDump` wrote. |
| `outputFolder` | path | Root the route keys are relative to (the unpacked tree). |
| `overwrite` | bool | Replace existing `.rel` files. |
| `engines` | paths *(optional)* | Engine folders resolving the sources' typed chunks. |

**`nkitBuild`** *(flat)* — shrink a raw GameCube ISO into a `.nkit.iso`.

The files are packed together and each run of junk between them is
replaced by a short marker, so a 1.46 GB disc typically comes out at a
fraction of its size — Pokemon XD US shrinks to 1.09 GB, the same
bytes NKit v1 itself produces.

An ISO carrying data at `0x200`-`0x21B` — where the NKit header block
goes, padding inside the game-title field on every retail disc — is
refused rather than shrunk lossily. So is a gap that no gap encoding
can express (neither pure junk nor a single fill byte, and not a
multiple of 256 bytes long); the error names its offset.

The input is read through a window rather than loaded, so peak memory
is the size of the image being *written*, not the sum of both.

### WIA / RVZ disc images

Not generated by project setup — hand-authored only. (Passing a `.rvz`
or `.wia` directly to `GODDESS` also auto-converts during project
setup.)

**Read only.** GoD-Tool restores these images and never writes one:
producing an RVZ needs a Zstandard *encoder*, and the package has only a
decoder. Which variant a file is comes from its magic — Dolphin writes
`"RVZ\x01"` for the newer one and `"WIA\x01"` for the older — not from
the extension, because Dolphin reads either under either name. The magic
also decides the group table's stride (12 bytes against 8), so it is
read rather than inferred.

**Zstandard and uncompressed images only.** A WIA using bzip2, LZMA or
LZMA2 is refused by name, as is the legacy PURGE mode; every RVZ
Dolphin writes today is Zstandard. A Wii image is restored in full —
each partition's decrypted payload is re-hashed into a fresh
H0/H1/H2 tree, the stored hash exceptions are applied over it, and the
result is re-encrypted with the title key the file carries (already
decrypted, so no Wii common key is needed). H3 is *not* recomputed: it
lives in the partition's unencrypted header, which the image stores
verbatim.

**`rvzDump`** *(flat)* — restore a raw ISO from a `.rvz` or `.wia`.

| Field | Type | Meaning |
|---|---|---|
| `rvzPath` | path | Input `.rvz` or `.wia`. |
| `isoPath` | path | Restored `.iso` output. |
| `overwrite` | bool | Replace existing output. |

The output size comes from the image's own `iso_file_size`, and the
file-header, disc-struct and partition-table SHA-1s are all checked
before any group is read, so a damaged image fails before it writes
anything.

### GCI save envelope

**`gciDump`** *(container)* — split a `.gci` memory-card save.

- `dumpGCI` — writes `gci-manifest.json`, one `.bin` per region, and the
  card's banner and icon frames as PNGs under `Card/`.

  | Field | Type | Meaning |
  |---|---|---|
  | `gciFile` | path | Input `.gci`. |
  | `outputFolder` | path | Output folder. |
  | `overwrite` | bool | Replace existing output. |
  | `saveEngine` | path *(optional)* | Engine folder declaring this game's save-card shape. When absent the shape is looked up from the gamecode. |

**Works for any GameCube save, not only Pokémon ones.** The banner, the
animated icon and the two comment strings are described by the save's own
directory entry, so they are located and decoded without knowing which
game wrote them.

The body splits on a region list. A game engine that knows the save's
shape declares one — that is the only way to find boundaries nothing in
the file describes, such as Pokémon XD's save slots at `0x6000` and
`0x2E000`. Without a declaration the list is derived: a `metadata` region
covering the images and comments, and a `data` region for the rest.
`layoutSource` in the manifest says which was used.

| Save | Regions |
|---|---|
| Pokémon XD | `metadata`, `slot-a.bin`, `slot-b.bin` |
| Pokémon Colosseum | `metadata`, `slot-1.bin`, `slot-2.bin`, `slot-3.bin` |
| any other game | `metadata`, `data.bin` |

A game-data region is written whole as `<name>.bin`. **The metadata
region gets no file at all**: it is rebuilt from scratch out of the
images, the comments and any checksum, with the rest set to the region's
declared fill byte. Nothing of the original save is carried into the
rebuild, so the rebuilt save is derived end to end rather than patched.

That only works if every byte of the region is accounted for, so the dump
checks it: the images and comments must re-encode to exactly the bytes
they came from, and everything else must already equal the fill. A save
that fails either check is refused with the offsets named, rather than
dumped with a hidden copy of the bytes that could not be explained. All
61 distinct real saves measured pass.

Slot bins are still encrypted at this stage; the per-game save operations
below decrypt them.

Inside `Card/`, the banner is `banner.png` and each live icon frame is
`icon-<slot>.png`. Frames are numbered by their field position, which may
have gaps — Luigi's Mansion uses slots 0, 3 and 7. **A paletted image is
written as an indexed PNG and has to stay one**: an RGBA PNG cannot say
which index held which color, and an animated icon's frames share a single
palette, so re-indexing each frame on its own gives one palette per frame
where the format holds one — the rebuild refuses it
(`sharedPaletteMismatch`), and forcing them onto a common palette would put
any color the first frame lacks on index 0. Edit the PNGs in something that
keeps them indexed.

`summary` in the manifest is a readable view of the directory entry and
is regenerated on every dump; `header` is the authoritative copy.

**`gciBuild`** *(container)* — reassemble a `.gci`.

- `buildGCI` (`inputFolder`, `gciFile` output, `overwrite`).

Concatenates the regions in offset order. The metadata region is built
from scratch: filled with its fill byte, then written over with the
re-encoded images and comments. Any integrity rule the manifest carries
is applied last, over the assembled body. Pokémon XD and Colosseum keep a word sum of their
metadata at `0x3A40`, so editing a banner or a comment means recomputing
it; replaying the dumped value would produce a save the game rejects.

A project dumped before the generic card layout has `banner.bin`,
`header0.bin` and `header1.bin` instead of `metadata.bin`. Those cut the
first icon frame in half. Re-run the dump to migrate; the build names
this case rather than reporting a decode failure.

### Save sections

Sub-section typing, run as its own pass either side of the save dump/build: the
save operations write and read one raw `.bin` per section, and these decompose
and recompose it. The binary is never deleted — the normal flow is
`xdSaveDump` → `saveSectionsDump`, and in reverse `saveSectionsBuild` →
`xdSaveBuild`.

It exists because some sections aren't describable by a section type. XD's flag
section needs a descriptor table from `common.rel` to know where one flag ends
and the next begins; Colosseum's flags sit at an offset *inside* a larger
section. Both are byte ranges within a section, which is what the layout file
describes.

**`saveSectionsDump`** *(container)* — decompose described sections into typed
artifacts.

- `dumpSaveSections`
  | Field | Type | Meaning |
  |---|---|---|
  | `slotFolder` | path | The slot folder holding the section `.bin` files (`Source/Save/Latest Slot`). |
  | `overwrite` | bool | Replace existing artifacts. |
  | `layout` | path | The section layout JSON. Project setup installs the game's own at `Engines/<game> Engine/Resources/save_section_layout.json`. |
  | `engines` | path[] | Engine folders whose structs resolve the layout's `struct`/`table` chunks, priority order — same convention as `convert` and the REL type maps. |
  | `flagsTable` | path *(optional)* | The flag descriptor table. Needed only by `flags` chunks. |

Artifacts go into a folder named after the binary's stem (`08-Flags.bin` →
`08-Flags/`), one file per chunk. **Bytes no chunk claims are written verbatim
as `gap-<offset>.bin`**, so a layout that describes only part of a section is
still lossless and can be extended later without breaking anything.

**`saveSectionsBuild`** *(container)* — recompose each described section's
`.bin` from its artifacts (`buildSaveSections`, same fields). Every byte comes
from an artifact, chunk or gap — nothing is inherited from the binary being
overwritten.

#### The decoded-flag CSV

Two columns: **`id,value`**. A flag's bank, bit position and width are all
derivable from the flag table, so they aren't repeated here — the file carries
only what is actually the save's data. Rows are matched by `id`, so a partial or
reordered file works; an `id` the table doesn't define is an error rather than a
silent no-op.

A flag is not always a boolean — 149 of XD's 2324 are 2 to 32 bits wide, and
`value` is the whole field. Widening a flag, or inserting one, is a change to
the *table*, not the save: bit positions are a running total per bank in table
order, so everything later in that bank shifts.

#### The section layout

```json
{ "sections": { "Flags": { "chunks": [
    { "flags": { "name": "flags", "offset": 0, "banks": [
        {"name": "FlagLevel0", "length": 32},
        {"name": "FlagLevel1", "length": 128},
        {"name": "FlagLevel2", "length": 1536} ] } },
    { "struct": { "name": "tail", "offset": 1696, "type": "XDSaveFlagsTail" } }
] } } }
```

Sections are keyed by the name the engine's `saveSections` declares, so a layout
survives a section being renumbered. Chunks are `flags`, `struct` or `table`,
each with an `offset` within the section; lengths come from the struct (or the
banks), and overlapping or out-of-bounds chunks are rejected rather than
silently clipped.

**Flag banks can be addressed by property instead of offset**, for a section
that dumps as typed JSON rather than raw bytes. Colosseum needs this: its flags
live inside `Tail`, which is a struct, so there is no `.bin` to slice and the
banks are already named byte arrays in the artifact. Give each bank a `field`
and omit the chunk's `offset`:

```json
{ "flags": { "name": "flags", "banks": [
    {"name": "FlagLevel0", "length": 32,   "field": "flagLevel0"},
    {"name": "FlagLevel1", "length": 128,  "field": "flagLevel1"},
    {"name": "FlagLevel2", "length": 1536, "field": "flagLevel2"} ] } }
```

For these the **CSV is authoritative**: the build writes the decoded values back
into those properties of the section's JSON, so editing the arrays there
directly has no effect. Every other property is left exactly as it was.

| `range` | object *(optional)* | Applied to every file; a file the window doesn't fit is an error. |

**`options`** — every field is optional. A field set for a format or
direction that doesn't read it is an error, not silently ignored.

| Field | Type | Applies to | Meaning |
|---|---|---|---|
| `alignment` | int | `yaz0`, compress | The header's alignment word. `0` (the default) for GameCube and Wii content; used from the Wii U on. |
| `deferredMatching` | bool | `yaz0` / `yay0`, compress | Nintendo's one-byte deferral heuristic. Default `true`. |
| `maxChainLength` | int ≥ 1 | `yaz0` / `yay0`, compress | Most match candidates examined per position. The default covers the whole window; lower is faster and may compress less. |
| `windowBits` | int 1–15 | `lzss` / `lzss-raw`, both | LZSS window bits (EI): the window holds 2^`windowBits` bytes. Default `12`. |
| `lengthBits` | int 1–8 | `lzss` / `lzss-raw`, both | LZSS length bits (EJ). Default `4`. |
| `threshold` | int ≥ 0 | `lzss` / `lzss-raw`, both | LZSS threshold (P): a match of this many bytes or fewer is sent as literals. Default `2`. |

The LZSS geometry has to fit its two-byte back-reference —
`windowBits + lengthBits ≤ 16` — and the window must hold two lookaheads,
2^`windowBits` ≥ 2 × (2^`lengthBits` + `threshold`). The defaults are the
Genius Sonority parameters shared by Colosseum, XD and Battle Revolution; a
stream cut with any other geometry only decodes under that same geometry.

### Binary patches

Not generated by project setup — hand-authored only. Create a patch from the
difference between two files, or apply one. No engine folder is involved: a
patch format is fixed knowledge about a file layout, so the format name and
the patch's own magic fully determine the codec. Any two files will do — a
disc image, a `.rel`, a save, a texture.

| `format` | Patch | Detected by | Extension | Verifies | Reversible |
|---|---|---|---|---|---|
| `ups` | byuu's UPS: the XOR of the two files, stored as hunks at fixed offsets | `UPS1` | `ups` | source, result, itself | **yes** |
| `bps` | byuu's BPS: an instruction stream, so it can copy from anywhere in either file | `BPS1` | `bps` | source, result, itself | no |
| `ips` | IPS: offset-and-size records. Three-byte offsets, so nothing past 16 MiB | `PATCH` | `ips` | **nothing** | no |
| `xdelta` | VCDIFF (RFC 3284), what xdelta3 writes | `D6 C3 C4` | `xdelta` | each window, where the writer stamped a checksum | no |

**`createPatch`** *(flat)* — write the patch that turns one file into another.

| Field | Type | Meaning |
|---|---|---|
| `sourceFile` | path | The original file — what someone applying the patch will have. |
| `targetFile` | path | The modified file — what they should end up with. |
| `patchFile` | path | Where to write the patch. |
| `format` | string | One of the formats above. Named rather than derived: the output doesn't exist yet, so nothing can say what it should be. |
| `overwrite` | bool *(optional)* | Replace an existing `patchFile`. Default `true`. |

**`applyPatch`** *(flat)* — apply a patch to a file.

| Field | Type | Meaning |
|---|---|---|
| `inputFile` | path | The file to patch. |
| `patchFile` | path | The patch to apply. |
| `outputFile` | path | Where to write the result. The same path as `inputFile` is refused — the result is verified by reading back what was written, which the original has to survive for. |
| `format` | string *(optional)* | Absent reads the format from the patch's magic. A named format must agree with it. |
| `direction` | string *(optional)* | `forward` applies the patch, `reverse` undoes it. Only UPS can be reversed — it stores the XOR of the two files, so the patch that turns A into B turns B back into A; every other format says what the result's bytes are and not what they replaced, and refuses. Absent derives the direction from the patch's own sizes and checksums. |
| `ignoreChecksums` | bool *(optional)* | Patch a file that isn't what the patch was made from, reporting every checksum mismatch as a warning instead of refusing. Default `false`. |
| `overwrite` | bool *(optional)* | Replace an existing `outputFile`. Default `true`. |

#### What gets checked

A patch that carries a checksum of itself — UPS and BPS — is checked against it
before anything else is read, so a truncated download fails at the patch rather
than halfway through a disc. The input is checked next, where the format says
what the input should be. The result is then read back from where it was
written — not taken on trust from the thing that wrote it — and compared with
the checksum the patch declares for it; since the input matched, a result that
doesn't can only mean the codec is wrong, so the file is deleted rather than
left looking like a result.

`ignoreChecksums` turns both of those into warnings and keeps the file. Patching
a file the patch was not made from cannot produce the file the patch names, so
a flag that relaxed only the input check could never produce anything.

**IPS verifies nothing at all** — it carries no checksums, no source size and
no metadata, so nothing identifies the file a patch belongs to. **xdelta carries
no checksum of either whole file**, only one per window where the writer stamped
it (xdelta3 does), which is verified as each window decodes. Both say so in a
warning when applied, rather than letting the absence pass for a pass.

#### What the writers do, and don't

- **UPS** and **IPS** describe the target's bytes where they sit. A difference
  anywhere costs its own bytes in the patch, and data that merely moved is a
  difference.
- **BPS** is written linearly: runs the target shares with its source, and runs
  it doesn't. That is byuu's own "linear" creator, and it is correct and
  run-length compact, but it does not search for moved data. A *reader* handles
  all four of the format's actions, because other tools emit them.
- **xdelta** searches: a hash index over the source, sampled more coarsely the
  larger the source, so that a region that moved is one copy instruction rather
  than a rewrite. Addresses are written in the simplest of the format's nine
  modes, so nothing it writes depends on the address caches — a reader still
  implements them, because other writers use them.

A patch of a format whose writer can't express something is refused rather than
written wrong: a difference past 16 MiB cannot be an IPS record, and
`createPatch` says so instead of wrapping the offset.

#### What is refused in somebody else's patch

- xdelta: secondary compression (xdelta3's `-S`), a custom code table, and a
  window that takes its segment from the target instead of the source — each
  named, rather than misread. Every xdelta3 patch written without `-S` uses none
  of them.
- Any patch whose magic belongs to no format read here, which is named with the
  bytes found.

#### Memory

Creating any patch, and applying a UPS, IPS or xdelta one, costs a window
rather than a file: measured flat at ~28 MB for 199 MB files, against 416-613 MB
before the window buffers were pooled. Two exceptions, both the formats' own
doing: applying a **BPS** patch builds the whole target, because one of its
actions can copy from any earlier part of the output; and the **xdelta** writer
holds the patch it is building, because a window's length isn't known until its
matches are found. Applying a UPS patch also holds its hunk index — about 24
bytes per hunk, which is 600 MB for a patch that rewrites most of a disc.

### External programs

Not generated by project setup — hand-authored only. Runs a program on the
host machine as one step of a chain, so a config can reach a tool GODDESS
doesn't implement — a converter, a patcher, an emulator, a project's own
script — without leaving the config file. No engine folder is involved: the
operation knows nothing about what it launches.

There is **no shell**. Arguments are passed one array element per argument
and verbatim: nothing is split on spaces, quoted, glob-expanded or resolved
as a path. To use shell features, run the shell — `"executablePath":
"/bin/sh"` with `"arguments": ["-c", "…"]`.

The program never inherits GODDESS's own streams. It is given pipes for all
three, so it can't swallow keystrokes meant for the tool or interleave its
printing with the log.

**`runExecutable`** *(flat)* — run a program with the given arguments and standard input.

| Field | Type | Meaning |
|---|---|---|
| `executablePath` | path | The program to run. Must exist and have its executable bit set. |
| `arguments` | string[] *(optional)* | Launch arguments, one per element, passed verbatim. Absent runs with none. |
| `standardInput` | string[] *(optional)* | Lines written to the program's standard input, each followed by a newline. The stream is closed afterwards, so a program reading to EOF sees exactly these lines. Absent closes it immediately, which is what a program sees as no input. |
| `workingDirectory` | path *(optional)* | The directory the program runs in. Absent inherits GODDESS's own — wherever the tool was invoked from, not the project root — so set it when the program resolves its own relative paths. |
| `outputFile` | path *(optional)* | Where to write what the program printed to standard output. Absent keeps it in the log only. Written whether the program succeeded or not. |
| `overwrite` | bool *(optional)* | Replace an existing `outputFile`. Default `true`. |
| `failOnNonZeroExit` | bool *(optional)* | Stop the chain when the program exits non-zero. Default `true` — a step that failed shouldn't let the next one run on its output. A program *killed by a signal* is an error either way: it never chose a status, so there is nothing to tolerate. |

`executablePath` and `workingDirectory` follow the usual path convention,
resolving a `./` prefix against `rootFolder`. Everything inside `arguments`
is the program's business, so a relative path there resolves against
`workingDirectory` — not against `rootFolder`.

Whatever the program printed goes to the log: standard output as info
(visible with `verbose`), standard error as a warning. When it fails, the
tail of its standard error is quoted in the error.

```json
{ "enabled": "YES", "operation": { "runExecutable": { "config": {
  "executablePath": "/usr/local/bin/vgmstream-cli",
  "arguments": ["-o", "./Build/bgm.wav", "./Source/bgm.ish"],
  "workingDirectory": ".",
  "outputFile": "./Build/vgmstream.log",
  "overwrite": true,
  "failOnNonZeroExit": true
} } } }
```

## Configs generated by project setup

Running `GODDESS <game>.iso` creates `"<name> project"` next to the input with
ready-to-run configs (see the README for the folder layout):

- **`/Config/Dump-Config.json`** — `gamecubeDump → unpackISO` (enabled), the
  game-specific asset dump (`dumpColosseum`/`dumpXD` enabled; the per-asset
  dumpers present but disabled), `commonRelDump` (enabled for Colo/XD), map
  REL batch dumps (present, disabled), and a final `dolDisassembly`
  (enabled). Wii discs get `wiiDump → decryptISO` (+ `pbrDump` for PBR)
  instead of the GameCube unpack.
- **`/Config/Build-Config.json`** — the mirror image: disabled
  `commonRelBuild`/map-REL builds, the game asset rebuild
  (`buildColosseum`/`buildXD` enabled, per-asset builders disabled), then
  `gamecubeBuild → buildISO + fillISO` (or `wiiBuild`) enabled.
- **`/Settings/Settings.json`** — `{ "verbose": false }`, plus
  `wiiCommonKeyFile` for Wii discs.
- **`/Scripts/Dump.sh`**, **`/Scripts/Build.sh`** — one-line launchers that
  invoke `GODDESS` with the matching config.

Running `GODDESS <save>.gci` creates `"<name> save project"` with
`Save-Dump-Config.json` (`gciDump` then the game's save dump) and
`Save-Build-Config.json` (the game's save build then `gciBuild`, writing
`<stem>_rebuilt.gci`), plus matching scripts.

Any GameCube save opens a project. A save from a game with no dedicated
support still gets its banner, animated icon and comment strings as
editable artifacts, and rebuilds byte-identically; only the per-game slot
steps are omitted.

Copy a generated config to a new file before customising it — project setup
may be re-run, and the generated files double as canonical examples of every
operation's path conventions.
