# Map REL — Floor Tables

Every map in Pokémon Colosseum and XD is a REL module whose data section holds
the map's *floor tables*: who stands where, where the player enters, the
camera, the lighting, screens that show video, and (once) a berry list. This
document describes each table, field by field, for both games.

GODDESS types these tables through the per-region REL route tables
(`Resources/rel_routes_<region>.json`, generated by
`scripts/analysis/gen_rel_routes.py`); the per-file assignment is in
[REL Routes - Per-File Analysis](REL%20Routes%20-%20Per-File%20Analysis.md).

## How a map hands its tables to the game

A map REL carries no table of contents. Its `_prolog` stores a pointer to each
of its tables into a DOL global, and the game reads the tables back through
those globals. The REL holds the reference — a module-0 relocation on the
store whose addend is the global's DOL address — and the DOL holds nothing
about any REL: the globals are plain pointer variables, null until a map's
prolog fills them.

Each list-shaped table is followed (after all the tables) by its count word
and an 8-byte header `{&count, &table}`; the header is what gets registered,
and the game walks `header → count` and `header → table`. A headerless table
(render data, berries) is registered directly, its count beside it.

| | XD | Colosseum |
|---|---|---|
| Globals named | yes — `relglobal.o` in the symbol map: `floorCharTbl_<map>`, `floorCharTbl_<map>_number`, `floorCharTbl_<map>_top` | no — names were copied from XD by position and are wrong |
| What a global *is* | its name | `common.rel`'s `Rooms`: each room points at the globals for its render, character, warp, camera and offscreen data |
| Room → table | room +0x08 render, +0x0C characters, +0x10 positions, +0x14 camera, +0x28 offscreen | room `render_data_pointer`, `character_data_pointer`, `warp_point_data_pointer`, `camera_data_pointer`, `unknown_data_pointer` |

In GODDESS every table is a CSV and every count word a derived `count` chunk:
the dump links the map's own count symbol to its table, and the build writes
the table's row count there. Nothing about a map's layout is assumed — which
tables a map has, in which order, is per file.

## Evidence

Field names come from the game's accessors wherever one exists — XD names
nearly all of them (`floorCharacterBios*`, `floorDataBios*`,
`floorFieldCamera*`, `floorOffscreen*`). Colosseum's map names none; its
character and render readers were found because its character-init and
talk-check routines mirror XD's step for step. Every field was checked against
every row on the US, PAL and JP discs. Descriptions below say which kind of
evidence each name rests on:

- **code** — read by a named or identified routine, with the use stated;
- **match** — the same position and value range as a code-confirmed XD field,
  with no Colosseum reader located;
- **data** — inferred from values alone;
- **unread** — nothing in the game reads it.

## Character — 0x24 bytes (both games)

XD `floorCharTbl`, Colosseum `Characters`. One NPC or object.

| Offset | Field | Type | XD | Colosseum |
|---|---|---|---|---|
| 0x00 | `flags` | u8 | see below | see below |
| 0x01 | `behavior` | u8 | see below | see below |
| 0x02 | `unknown_0x02` | u8 | unread; 0 | 0–4 on a few characters; no reader found |
| 0x03 | `animation_id` (XD) / `unknown_0x03` | u8 | code: starting animation, `setAnimIndex`; 3 on most | 0 everywhere |
| 0x04 | `angle` | s16 | code: facing in degrees (`GetRot`) | code |
| 0x06 | `people_info_id` | u16 | code: people info → model (`GetPeopleInfoPtr`) | code |
| 0x08 | `name_id` | u16 | code: index into `PeopleIDs` (`GetNameID`) | data |
| 0x0A | `unknown_0x0A` | u16 | padding: the game's record copy skips it | 0 |
| 0x0C | `unknown_0x0C` | u32 | unread; 1 on map characters, 0 on the three built-in ones | 1 |
| 0x10 | `move_script_function` | u32 | code: run continuously (`GetMoveSctID` → `peopleExecMoveScript`) | data |
| 0x14 | `talk_script_function` | u32 | code: run when talked to (`GetTalkSctID`) | data |
| 0x18 | `x` / `y` / `z` | f32 ×3 | code: position (`GetPos`) | code |

The script fields are one 32-bit function id each, handed to the script
engine's `runParams` on the map's script or the common script. On disc they
are `0x01000000` + the function's index in the map's own script; 0 is none.
The legacy GoD tool split each into a "has script" byte and an index — a split
a common-script id (top byte `0x05`) would not survive.

### The flag bytes

Packed differently in the two games. The legacy tool read both with XD's
layout, so its Colosseum movement values were wrong.

| | XD | Colosseum | Evidence |
|---|---|---|---|
| visible | byte 0 bit 7 | byte 0 bit 7 | code (`GetVisibility` → `peopleSetDisp`) |
| placed when the floor loads (else a script places it) | bit 6 | — | code (`GetLoadInit`) |
| has collision | bit 5 | bit 6 | code (`GetIsHit` → `peopleSetCollision`) |
| head follows the player | bit 4 | bit 5 | code (`peopleMoveNeckTargetHero`) |
| can be talked to through walls | bit 3 | bit 4 | code (`GetTalkWallThrough`) |
| animation blending | bit 2 | — | code (`GSmodelEnableAnimBlend`) |
| unread | bits 1–0 | bit 3 (set once) | |
| move type | byte 1 bits 7:5 | byte 0 bits 2:0 | code |
| talk start | byte 1 bits 4:3 | byte 1 bits 7:6 | code |
| talk end | byte 1 bits 2:1 | byte 1 bits 5:4 | code |
| unread | byte 1 bit 0 | byte 1 bits 3:0 | |

- **Move type** — 0 stands, 2 random walk (`peopleStartWalkRandom`), 3 random
  rotation (`peopleStartRotRandom`); 1 and 4 start nothing when placed (4 does
  occur on disc).
- **Talk start** — 0 doesn't react; 1 turns its head toward the player; 2
  saves its facing and turns its whole body (`peopleRotateToTarget`); 3 can't
  be talked to (`peopleTalkCheck` skips it).
- **Talk end** — 0 keeps facing the player; 1 turns back to the saved facing
  (`peopleRotateToAngle`). Only matters with talk start 2; a head turn always
  relaxes.

The struct system has no sub-byte fields, so `flags` and `behavior` are u8
columns carrying these descriptions.

## Entry point / position — 0x10 bytes (both games)

XD `floor_pos_list`, Colosseum `EntryPoints`. Where a warp lands the player.

| Offset | Field | Type | Evidence |
|---|---|---|---|
| 0x00 | `angle` | s16 | code: facing in degrees on arrival (`floorDataBiosGetPosListData`) |
| 0x02 | `unknown_0x02` | u16 | padding: unread, 0 |
| 0x04 | `x` / `y` / `z` | f32 ×3 | code |

## Render setup

XD `floor_resource_data` (the game's name; the struct is `FloorRenderData`),
Colosseum `RenderData`. The map's lighting, shadow and fog choices, naming
models and lights by resource id (`0xGGGG10xx`).

| Offset | Field | Type | Used by |
|---|---|---|---|
| 0x00 | `sun_res_id` | u32 | `_floorInitScene`: the model whose position is the lens-flare sun |
| 0x04 | `shadow_light_id` | u32 | `peopleSetInfo` & co.: the light that casts character shadows |
| 0x08 | `shadow_receive_ids` | u32 ×8 | `_peopleUpdateShadows`: models character shadows fall onto; 0 ends the list |
| 0x28 | `secondary_render_ids` | u32 ×3 | XD only — `floorInitMap`: models moved to another render layer |
| 0x34 | `fog_exempt_model_ids` | u32 ×3 | XD only — `_floorInitMapFog`: models drawn without fog |
| 0x40 | `unknown_0x40` | u32 ×2 (×3) | XD only — unread |

| Variant | Size | Struct |
|---|---|---|
| Colosseum | 0x28 | `FloorRenderData` — ends after the shadow receivers |
| XD | 0x48 | `FloorRenderData` |
| XD prototype maps (`TEST000`–`004`, `B1_2/3/6`, `tv_test`, `waza_viewer`; on JP also `B1_1`, `peopleViewer001`) | 0x4C | `FloorRenderData4C` |
| XD's leftover Colosseum-format maps | 0x28 | `FloorRenderDataColosseumFormat` |

The legacy tool's "group id" at +8 is the top half of the first shadow-receive
resource id; it never matched a map's FSYS group id.

## Field camera

XD `floor_field_camera_list` — 0x34 bytes. While the player is inside a
camera's area, the camera sits at its distance, height and angle; between
areas the game blends (`floorFieldCamera`).

| Offset | Field | Type | Evidence |
|---|---|---|---|
| 0x00 | `area_shape` | u8 | code: 0 a circle of radius `area_size`; otherwise a box |
| 0x01 | — | pad ×3 | 0 everywhere |
| 0x04 | `center_x` / `center_y` / `center_z` | f32 ×3 | code (the area test is flat and ignores y) |
| 0x10 | `distance` | f32 | code: `cameraSetDistance` |
| 0x14 | `height` | f32 | code: `cameraSetHeight` |
| 0x18 | `rotation_y` | f32 | code: `cameraSetRotY`, radians |
| 0x1C | `area_size` | f32 | code: circle radius, or the box's half-width |
| 0x20 | `area_depth_ratio` | f32 | code: box half-depth = `area_size` × this |
| 0x24 | `area_rotation` | f32 | code: box rotation, radians |
| 0x28 | `transition_easing` | f32 | code: exponent of the ease curve, `pow(1 - cos(…), this)` |
| 0x2C | `transition_time` | f32 | code: seconds to blend in; a negative value on any camera keeps the floor in path mode |
| 0x30 | `fov` | f32 | code: `cameraSetFov`, degrees |

Colosseum `FieldCameras` — 0x18 bytes: six floats matching XD's +0x04…+0x18
by position and value range (**match**): `center_x/y/z`, `distance`
(100–141 on disc), `height` (24–97), `rotation_y` (mostly 0). No area,
transition or field-of-view fields.

## Offscreen data

XD `floor_offscreen_data_list` — 0x14 bytes. A model or movie rendered into a
texture that replaces a map model's texture — a TV, a monitor
(`floorSetOffscreenIndex`).

| Offset | Field | Type | Evidence |
|---|---|---|---|
| 0x00 | `source_kind` | u8 | code: 0 an animated model (`floorOpenModel`), otherwise a movie (`GSmoviePlay`) |
| 0x01 | `animation` | u8 | code: the model's animation index, or for a movie non-zero loops it |
| 0x02 | `id` | u16 | code: what `floorSetOffscreenIndex` selects by |
| 0x04 | `texture_width` / `texture_height` | u16 ×2 | code: `GStextureCreate`; 192×144 or 256×256 on disc |
| 0x08 | `target_model_res_id` | u32 | code: model whose texture is replaced (`GSmodelSetTextureChange`) |
| 0x0C | `source_res_id` | u32 | code: the model or movie rendered |
| 0x10 | `held_res_id` | u32 | code: fetched and held while active; nothing else reads it |

Colosseum `OffscreenData` — 0x18 bytes. `texture_width`/`texture_height` at
+0 (256×256 on every entry — **match**), `id` at +4 (**match**), then three
resource ids at +8, +0xC, +0x14 and a small value (0–3) at +0x10 whose roles
are not confirmed (`unknown_*`).

## Berries — 4 bytes (both games)

XD `kinomiData` (only `M3_out` has one), Colosseum `BerryWeights`.

| Offset | Field | Type | Evidence |
|---|---|---|---|
| 0x00 | `item` | u16 `Items` | data: every value is a berry |
| 0x02 | `weight` | u16 | data: 83–333; no reader found |

## What stays raw

Every list header (`{&count, &table}`) is assembly — two pointers, rebuilt
symbolically. The menu modules' tables (`pda_menu`, `mail`, `toolbattle_menu`,
`worldmap_menu`) have no struct yet; `pocket_menu`'s four are typed in both
games — see [pocket_menu.rel - Shop Tables](pocket_menu.rel%20-%20Shop%20Tables.md). Nothing
else in any map REL of either game is raw.
